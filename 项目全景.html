先说结论

这套系统里没有地图、没有定位、没有「环岛算法」。它每 33 毫秒看一次画面，把「路偏了我多少」算成一个 −1 到 +1 的数字，再按这个数字打方向。所有看起来复杂的行为，都是从这一个数字加几条优先级规则里长出来的。 后面 17 节，就是在解释这一句话。

序 / 零基础

完全不懂？先花三分钟看这一节

后面每一节都在讲细节。这一节只回答三个问题：这是什么东西、它由哪些部件拼起来、它凭什么能跑。

一句话版本

一个学生比赛用的项目：让一辆玩具大小的车，只靠一颗 USB 摄像头，沿着地上一片白色的路自己跑完整条赛道； 路上还要做对四件事——看到黄线停稳、绕开红色路锥、不闯红色禁行区、把地上的数字压住。 全部代码跑在一块巴掌大的板子上，没有遥控器，比赛过程中人不许干预。

它的全部智慧，可以压缩成一个动作

想象你推着购物车往前走，低头只看得到脚前一米宽的一条白色地胶。任务：让车轮始终压在这条地胶的中间。 地胶偏左了，你就把车往左带一点；偏右了，就往右带。偏得越多，带得越狠。

这辆车做的就是这件事的机械版：它每 33 毫秒看一眼前方地面，算出「路的中心比画面的中心偏了多少」， 把这个偏差变成一个转向力度，发给轮子。偏差是 +0.30 就往右带一点，是 −0.50 就往左带得多一些。

它不会做的三件事

① 不认路——地上画着数字，但它只关心数字在哪，不关心是几（第 08 节解释为什么）。
② 不记路——没有地图、没有 GPS、没有「我上次来过这里」。
③ 不规划——它不知道终点在哪，只知道「此刻该往哪打一点方向」。
结果是：每一帧，它都当成第一次看见这条路。好处是简单、稳、不容易崩；坏处是换个场地就得重新调阈值。

问题三：它凭什么不会冲出去？

靠两样东西，都很朴素：

  1. 看得清「现在偏了多少」。它不去算整块白色区域的重心（那样一到岔路口就会被带偏）， 而是在画面里横向扫两条带子，找「连续、够宽、离我最近的那条白色通道」，再把两条带子的结果按 7:3 加权。 这一步的产出只有一个数：error，范围 −1 到 +1。（第 05 节）
  2. 偏多少就反打多少，但打满为止。转角 = −kp × error，超过上限就砍掉。 偏得越狠转得越急，同时速度自动降低——因为速度越快，同样的转角画出的弧线越大，越容易冲出赛道。（第 06 节）
为什么「打满为止」很重要：如果没有上限，偏一点点就会要求一个物理上做不到的转速， 车会在直道上左右抽搐（行话叫「画龙」）。加上限，等于承认「车的极限就这么大」，剩下的靠减速补。

顺便看一眼：一场比赛从头到尾是什么样

上面讲的是「每一刻它怎么想」。下面是「一整场它怎么过」——这张表基本就是它的全部人生：

阶段车在做什么会不会停
① 上电8 个程序按固定顺序启动，一个等一个。相机已经在拍，但车一动不动不动（零速）
② 按下空格收到「可以走了」的信号，开始以 0.4 m/s 前进——这一步之前谁按都没用，防抢跑开始动

00 / 摘要

90 秒看懂：它在做什么

把这辆车当成一个上班的人，它每天只干五件事，按固定优先级排队：

优先级看到什么就干什么谁负责
1画面里有一大片黄色立刻刹停，停 1 秒；第 4 次遇到黄线则永远停（比赛结束）line_follower
2车前有红锥 / 红线往反方向让一点，同时减速，但绝不停车（红锥没有停车权）line_follower
3数字出现且快被车压到朝数字打一把方向，把数字压在轮子底下detection_turn_controller
4白色路面跟着白路走，偏多少就反打多少line_follower
5什么都没有（丢线）不慌，按上一帧的方向继续低速蹭 0.8 秒line_follower
翻译：这不是一个"自动驾驶"系统，而是一个反射式状态机。它没有"我要去哪"的概念， 只有"此刻眼前是什么，按规矩该反应什么"。所以它跑得稳，但换个场地就得重调阈值。

三个数字，决定了它全部的性格

kp = 2.45无量纲
路面中心偏出半个画面宽时，它想要 2.45 rad/s 的转速——这已经超过车的物理极限，所以实际上偏到 61% 就打满舵。这是"急脾气"。
target_speed = 0.4m/s
1.44 km/h，大约是人类散步速度的三分之一。500 cm 的赛道理论上 12.5 秒跑完，实际上因为 8 次停车，会拖到分钟级。
max_yaw_rate = 1.5rad/s
86°/s。和 0.4 m/s 一起，恰好算出 0.267 m 的转弯半径——正好卡在赛规"最小转弯半径 0.3 m"的物理边缘上。
为什么这个洞察重要

0.4 ÷ 1.5 = 0.267 m。这说明参数不是拍脑袋填的，而是反推出来的：先用赛规的最小转弯半径定死底盘极限， 再用速度去凑这个极限。任何"把 target_speed 提到 0.6"的调参，都会让满舵半径变成 0.4 m， 在 500 cm 的小场地上直接切进内道压线（压线一次 +15 s）。

01 / 背景

这场比赛到底在考什么

先看规则，才能理解代码为什么长成这样。很多"奇怪的设计"，答案都在赛规里。

赛道
单起点、单终点有向无环图（DAG），两张地图：岔路、环岛，各 500 × 300 cm。
五大环节
分叉 → 汇合 → 避障 → 规则遵守 → 奖励获取。
地面
白色路面 + 黑色边界线。出黑线即"冲出赛道"，成绩无效。
计分
综合得分 = 计时得分 + 总罚时 − 5 × Bonus。分数越低排名越高。
评分方式
每张地图跑 3 次，取最好的一次。两次都翻车，第三次才有意义。

赛规里藏着的一条"战略结论"

停稳一次 15 s，撞一个锥 10 s，压一次线 15 s（而且是每持续 1 秒算一次，不足 1 秒向上取整）。 一个 Bonus 才 −5 s。换算下来：为了多拿一个数字而冒撞锥风险，是稳亏的买卖。 这就是代码里"红锥只减速不让行、丢线不停车、宁可慢慢蹭"这一整套保守策略的由来—— 不是技术上做不到更快，是算分算出来不该更快。

于是代码的形态被这三条约束锁死了

  1. 必须能"看见黄线就停" → 需要一路独立于巡线的颜色检测，且优先级最高、能覆盖一切。
  2. 不能压线 → 需要一个稳定的横向误差，且弯道必须减速（高速 + 大转角 = 切内道）。
  3. 不能撞锥 → 需要"越近推力越大"的软避障，而不是"看到就急转"（急转本身就是压线）。

03 / 上电

启动时序：为什么必须一个等一个

这不是仪式感。ROS 2 的话题是先发布后订阅就会丢，摄像头设备号可能还没枚举完，串口可能还没打开。

比赛用的不是 ros2 launch 一条命令，而是 tools/start.sh。它的核心逻辑很朴素： 启动一个，等它的日志里出现某句话，再启动下一个。

tools/start.sh（精简）
start_proc  "base"    ros2 launch turn_on_wheeltec_robot ...
wait_log    "serial port opened"        # 串口没开，后面全是空转

start_proc  "camera"  python3 src/camera/camera.py
wait_log    "摄像头已成功启动"            # /dev/video0 可能还没就绪

start_proc  "yolo"    python3 src/yolov8/bpu_yolov8_node.py
wait_log    "视觉检测节点就绪"            # BPU 模型加载要几百毫秒

start_proc  "follow"  ros2 launch line_follower line_follower_with_detection.launch.py \
                      params_file:='$PARAMS_FILE'
wait_log    "Line follower subscribing"  # 订阅建立，图像不会白丢

start_proc  "start"   ros2 run line_follower start_toggle_node   # 最后才给发车开关
start_proc  "panel" / "safety" / "collector"
翻译：这就是"开机自检"。每一步都在确认上一步真的活着，而不是"命令发出去了"。 因为如果相机晚启动 2 秒，巡线节点会以为"没路"，一开始就按丢线逻辑乱走。

两个细节，看得出是踩过坑改出来的

  • 发车开关是 10 Hz 持续发的，不是按一次发一次。因为 start_cmd 没有用 transient_local（易失 QoS）， 后启动的订阅者收不到历史消息。持续发，等于用"刷屏"来保证对方一定能收到。
  • 参数只从 tools/config/*.yaml 注入。包里自带的 config/line_follower_params.yaml 只是模板， start.sh 用 params_file:=$PARAMS_FILE 覆盖了它。所以改包里的 yaml 不生效，这是最常见的"改了没用"。

④ 形态学：先擦掉小污点，再补上裂缝

06 / 决策

打方向：一根弹簧，没有 PID

全车的核心公式只有一行。它没有积分项、没有微分项，也没有抗饱和处理。

// 速度只做一件事：偏得越多越慢（弯道减速）

为什么"没有 PID"反而可能是对的

PID 的 I（积分）用来消除稳态误差，D（微分）用来抑制超调。但这套系统的输入每 33 ms 就换一次， 而且误差本身就是有噪声的（游程中心会随反光轻微跳动）。加 D 项等于把噪声放大， 加 I 项在弯道会产生"积分饱和"——出弯后车会朝反方向甩一下，直接压线。 纯 P 在慢速场合是性价比最高的选择：简单、可预测、不会积累。

数字识别：它不是在认路，是在"瞄准压线"

这一节是整份文档里最容易理解错的地方。看完你会知道，为什么"识别出是数字几"其实不影响车怎么走。

先看代码到底用数字做了什么

转向公式里没有出现数字的值：yaw = clamp(-1 · x_diff · 1.6, ±1.3)。 数字识别结果只被用于两件事：① 打日志（best=%d）；② 多个候选框时挑一个记录。 真正决定往哪转的，是数字的 x 坐标相对于路中心的位置。

结论：这不是"看到 3 号数字就往第 3 个路口走"的决策系统。 它做的事是——发现地上有个数字，而且快要被车压到了，于是朝它打一把方向，把它压到轮子底下。 对应赛规的 Bonus 规则："小车完全覆盖数字即触发"。

三个"同时满足"才动手

  1. 置信度够：confidence ≥ 0.1（这个值被调得极低，宁可错认——因为错认不罚分）。
  2. 纵向对齐：|数字 y − 路中心 y| ≤ 0.01，即数字已经在车的正前方不远处。 这一条是核心：远处看到的数字不动手，等它快被压到才动。
  3. 累计够帧：连续 frame_window=2 帧都存在，才触发一次。
double y_diff = det_y_norm - last_centroid_norm_y_;      // 纵向差
if (std::abs(y_diff) <= 0.01) {                          // 只有"对齐"了才考虑
    double x_diff = det_x_norm - last_centroid_norm_x_;  // 数字在路中心的左边还是右边
    if (chosen.conf > best_conf_) { best_x_diff_ = x_diff; ... }
}

turning_end_time_   = now + 0.38s;
turn_cooldown_until_ = turning_end_time_ + 0.8s;
为什么必须"纵向对齐"：因为摄像头是斜着往前的，画面里的 y 坐标 ≈ 距离。 y 大 = 靠下 = 离车近。要求数字的 y 和"路中心的 y"接近，等于在问： "这个数字是不是正好在我即将经过的位置？"——是，才值得打方向；不是，等它靠近点再说。

09 / 仲裁

抢方向盘：cmd_mux 的三级优先

三路指令抢同一个 /cmd_vel。规则只有三条，但它决定了车"听谁的"。

cmd_mux_node.cpp:135（低优先级路径上做的判断）
void low_callback(const Twist::SharedPtr msg) {   // 巡线指令到了（30 Hz）
    // ① 停车最优先：最近 0.5 s 内收到过 stop，就一直发 stop
    if (has_stop_ && (now - last_stop_time_) <= stop_timeout_) {
        publish(last_stop_msg_);  return;
    }
    // ② 其次：最近 0.5 s 内收到过数字转向指令，继续用它
    if (has_high_ && (now - last_high_time_) <= high_timeout_) {
        publish(last_high_msg_);  return;
    }
    // ③ 都没有，才用巡线
    publish(msg);
}
翻译：这是一个 "话题级"的优先级仲裁，不是"投票"，也不是"加权平均"。 谁在有效期内，就独占方向盘。所以不存在"巡线和数字各转一点"这种混合——一定是其中一个说了算。

为什么不直接让 cmd_vel_stop 覆盖？

因为 ROS 2 的 topic 没有"优先级"概念，三个发布者往同一个 topic 发，接的人只会收到最新的那条， 顺序完全取决于调度。必须有一个中间人来做"选谁"，这个中间人就是 cmd_mux。

优先级话题保鲜期失效后会怎样
最高/cmd_vel_stop0.5 s按零速再飞 0.5 s，之后交还下一级
中/cmd_vel_detection0.5 s（launch 覆盖）回到巡线——但注意，这 0.5 s 是"白飞"的
低/cmd_vel_follower无（默认路径）—
"保鲜期"这个概念，是这套系统的灵魂

所有优先级都是基于时间而不是基于事件。这意味着：任何一路突然死掉，系统都会在超时后自动降级， 而不是卡死。代价是——超时期间车在用"过期数据"开车。所以超时值既是"安全垫"，也是"盲开时长"。
赛规里的"连续 30 s 无状态变化即终止"，对应的就是这个机制的下限。

为什么要 ×1000：整形数据传输不需要协商字节序和浮点格式，协议更简单、更抗错。 代价是精度只有 1 mm/s 和 1 mrad/s —— 对 0.4 m/s 的车来说完全够用（0.25% 的分辨率）。

上层拿到 angular.z 之后，谁负责把它变成舵机角度？

是下位机固件，而且固件闭源。上位机完全没有"角速度 → 前轮转角"的换算，也没有 "线速度 → 电机 PWM"的换算。它只是把 rad/s 原样塞进串口。
阿克曼的横摆角速度与转角的关系是 ω = v·tan(δ)/L（L 为轴距）， 这个 tan(δ) 由下位机按自己的标定表完成。这意味着：换底盘、换轮胎、改轴距时，上位机的参数全都不用动—— 这是这套架构最省事的地方，也是最"黑盒"的地方。

11 / 兜底

如果上位机突然死掉，车会怎样

答案：如果不加 safety_node，它会保持最后一次的速度，一路撞到东西为止。

一个真实的硬件缺陷

这块下位机固件没有指令超时保护。也就是说，它收到 "0.4 m/s 直行" 之后就一直执行， 直到收到下一条指令。上位机进程崩溃、SSH 掉线、USB 松动——任何一种情况都会让车"永动"。

软件层的补丁：看门狗

tools/safety_node.py
# 20 Hz 检查：如果三路速度指令都超过 0.3 s 没更新，就自己发一条零速
if now - last_seen > silence_timeout:      # silence_timeout = 0.30
    pub.publish(Twist())                   # 全零：linear.x = 0, angular.z = 0
为什么是 0.3 s：正常指令流是 30 Hz（33 ms 一条）。0.3 s 相当于连续丢了 9 条。 再短容易误判（网络抖动）；再长，车已经多跑了 12 cm（按 0.4 m/s 算）。
但这里有个结构性矛盾

safety_node 自己也是个 ROS 节点。如果它和巡线节点在同一个进程组里、或者整机供电挂了， 它也会一起死。所以它只能防"单个节点崩溃"，防不了"整机断电"或"USB 摄像头掉线导致的连锁失败"。 真正意义上的物理急停（继电器 / 遥控器）目前没有。

另外两道闸

  • 发车闸：line_follower 启动后 start_enabled_=false， 在收到 start_cmd=true 之前只发零速。这是防"上电就冲"的（赛规里叫抢跑，直接判无效）。
  • 永久停车闸：第 4 根黄线之后 permanent_stop_=true，此后任何控制都盖不住， 连重新发车也不会解除（除非重启节点）。这是防"跑完还在场上乱转"。

术语

ROI
Region of Interest，感兴趣区域。这里指"只看画面中间那一横条"。
HSV
色相/饱和度/明度。比 RGB 更适合按"颜色"切分，因为白色 = 低饱和 + 高明度，与亮度解耦。
Twist
ROS 标准速度消息：linear.x 前后 m/s，angular.z 自转 rad/s（逆时针为正）。
阿克曼
汽车式转向：两个前轮转角不同，绕同一个圆心转。特点是不能原地转，必须有速度才能转向。
deadman / 看门狗
持续收心跳，收不到就自动刹车。本项目的 safety_node 就是。
横摆角速度
就是 angular.z，车头绕竖轴旋转的快慢，单位 rad/s。和方向盘角度不是一回事。
转弯半径
r = v / ω。同样打满方向，越快半径越大；想在小场地拐小弯，只能减速。

读代码时会遇到的词

launch 文件
一份「一次启动多个节点」的配置单。本项目 tools/start.sh 调的就是它。参数也从这里注入。
colcon / 工作空间
ROS 2 的编译工具。colcon build 把 src/ 里的包编译到 build/ 和 install/，这两个目录不该进版本库（已被 .gitignore 排除）。
掩膜 / mask
一张只有黑白的图：把「符合颜色条件的像素」标白，其余标黑。找黄线、找红色都是先做掩膜。
形态学开/闭运算
对掩膜做的小修补：开运算擦掉孤立白点（去噪），闭运算把断开的白块连起来（补缝）。
质心
一片白色区域的几何中心。本项目故意不用整块区域的质心，因为岔路口会被拉偏。
夹紧 / clamp
把一个数限制在上下限之间。clamp(x, -1.5, 1.5) 就是「超过 ±1.5 就按 ±1.5 算」。
QoS / 易失
ROS 2 消息的投递策略。默认「易失」意味着后订阅的人收不到之前发过的消息——所以发车开关才要 10 Hz 一直发。
